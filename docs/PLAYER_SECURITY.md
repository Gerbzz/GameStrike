# GameStrike player boundary and next verification

## Present boundary

The library and future console-style launcher are trusted local UI. Imported HTML runs only in the separate Wry/WebView2 player process. The player has no Tauri command surface, IPC handler, host objects added by GameStrike, or generic bridge from game JavaScript to launcher actions. Its local asset handler accepts only the selected game's exact origin and canonical files inside that game's content directory. A distinct UUID-derived origin and WebView data directory are used per game. The included first-party save fixture verified `localStorage` persistence and separation across two game IDs under the guarded player build on this Windows PC.

Wry denies top-level navigation away from the selected origin, new windows, downloads, and permission requests in the player source. Direct WebView2 event handlers now also deny cross-origin frame navigation and cancel registered external URI launches. They are registered before loading game HTML, and launch fails if the required external-URI interface is absent. This addition passed a Rust source check and unit tests but **has not been run in a freshly built player**. Browser accelerator keys and default context menus are disabled. A drag/drop handler is installed; Wry's Windows documentation says its return value is ignored and the handler replaces WebView2 drag/drop handling, so this behavior needs a controlled check and may affect games that use HTML drag/drop. These callbacks alone have not been verified against every subframe, external protocol, worker, or WebView2 version path. A separate process is not a Windows sandbox. The player queries its Windows process token before WebView creation, accepts only medium integrity RID `0x2000`, and refuses failed, unknown, low, high, system, or protected results. It only reads the token; it never changes it. An elevated launcher must start a standard-integrity child or report the refusal. The player also calls WebView2 settings to disable host objects, web messages, and default script dialogs before navigating to game content. The earlier first-party fixture loaded after these calls, but a controlled JavaScript probe of each setting is still needed. [Microsoft's WebView2 security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security) recommends standard integrity and explicit restrictions.

## Network policy

Wry's top-level navigation callback is not a complete network filter. Strict offline mode is **unavailable** in this checkpoint. The player requires `--allow-network` for normal launch, and `--smoke` accepts only the exact bundled first-party save fixture. This is an explicit consent gate, not an offline mode or a claim that arbitrary downloaded games are safe. Imported games stay labeled `network: unknown`; users cannot infer offline compatibility from a successful import.

Microsoft's [`ICoreWebView2_22` documentation](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_22) provides a request filter with source kinds for frames, shared workers and service workers; it must be installed before main-page navigation. Cached Wry 0.57 uses that newer filter when available for its **game-origin custom protocol**, with a legacy fallback. It does not register a catch-all filter for remote URLs. A [tracked WebView2 issue](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4303) reports that `WebResourceRequested` does not fire for WebSocket connections; therefore, even a catch-all `WebResourceRequested` handler by itself is insufficient evidence of strict offline play. This remains a source/documentation finding, not a runtime network test on this PC.

Before offering offline play, implement and verify a policy that covers main frames, subframes, scripts, images, CSS, `fetch`, WebSockets, workers and service workers, beacons, forms, redirects, and external protocols. Keep one game-specific origin available for imported assets and block every other request; fail closed if the runtime lacks the needed hooks. Verify with a loopback server and network observation, including WebSockets, then repeat storage persistence tests. If any meaningful path bypasses the policy, keep strict offline unavailable. Network-enabled play remains a deliberate per-game choice with a clear disclosure.

## Trusted launcher path

A console-style launcher can use Tauri 2 for its own trusted UI, with capabilities scoped only to that launcher window. It should call Rust library methods to list/import games and spawn the separate player by validated game UUID. Game HTML must never be put in a Tauri webview or given Tauri capability access. Launch controls should display unknown controller and network requirements, ask for the network choice, and provide clear keyboard and gamepad focus states. Launcher gamepad navigation does not imply a game's controls support gamepads. No trusted launcher UI is implemented in this checkpoint.

## Remaining controlled checks

- Verify refusal under a controlled actual elevated-token process; current pure decision tests reject high/system RIDs, and the native test queried only a medium token. Do not alter a user's token or security settings for this test.
- Verify that normal player launch without `--allow-network` fails before WebView creation. The smoke-fixture unit test already rejects changed or extra files.
- Repeat save persistence after future browser policy changes; the guarded player already reopened the first fixture profile at launch 4 and the second at launch 2.
- Run the exact first-party `boundary-smoke.html` in the newly built player using `--boundary-smoke` and two game IDs. It probes a nonexistent local file, popup, permission, data-URI download, cross-origin frame, and storage count. Interpret page results alongside native callback logs; a rejected `fetch` alone does not prove every browser request path was blocked. No registered external protocol is invoked by the fixture.
- Probe host-object, web-message, dialog, download, permission, and frame/external-protocol behavior with controlled HTML. A successful fixture load confirms setter success, not every browser behavior.
- Check frame navigation, protocol handling, browser permissions, and local network access at runtime before expanding arbitrary-game support.
